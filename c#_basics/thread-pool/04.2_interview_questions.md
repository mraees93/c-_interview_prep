# Asynchronous Programming (async/await) - Interview Preparation

This module tracks asynchronous processing mechanics, synchronization contexts, task allocation states, and anti-patterns vital for highly responsive legal document processing APIs.

---

## 1. Async/Await Compilation Mechanics (Under the Hood)

### The Panel Question
What does the C# compiler actually do to an `async` method under the hood, and does declaring a method as `async` automatically execute it on a background thread?

### Core Answer
*   **The State Machine**: The compiler transforms your `async` method into an optimized **state machine structure** (implemented as a hidden `struct`). It splits your method code into distinct sections bordered by `await` boundaries.
*   **Thread Execution**: No, `async` does not automatically spawn a new thread. An async method executes synchronously on the calling thread until it reaches its very first `await` expression on an uncompleted task. Only then does the thread yield control back to the caller while the asynchronous I/O operation progresses.

## 2. Asynchronous Return Types: `Task` vs. `ValueTask`

### The Panel Scenario
High-throughput processing pipelines parse thousands of documents per second. Choosing the wrong asynchronous return type can generate massive object allocation overhead.

```csharp
// Option A
public async Task<bool> IsCachedAsync(string docId) { ... }

// Option B
public async ValueTask<bool> IsCachedAsync(string docId) { ... }
```

### Questions & Core Answers
*   **Q1: If the document data is already locally cached 95% of the time, which option optimizes memory?**
    *   **Answer**: **Option B (`ValueTask<T>`)**. A standard `Task` is a reference type allocated on the Managed Heap. Returning it repeatedly when data is already available synchronously creates unnecessary heap garbage. `ValueTask` is a value type structure allocated on the Stack, bypassing heap allocation entirely when the operation completes synchronously.
*   **Q2: When should you avoid using `ValueTask`?**
    *   **Answer**: Avoid `ValueTask` if you intend to await the exact same task instance multiple times, await it concurrently across separate paths, or call `.AsTask()`. It is designed for single-await execution sequences only.

## 3. Advanced Error Handling & Aggregation

### The Panel Question
How does exception handling differ when an unhandled failure occurs inside an `async Task` method compared to an `async void` method?

### Core Answer
*   **async Task**: The runtime catches the exception and wraps it securely inside the returned `Task` object. The exception is only thrown and observed when your code actively executes an `await` on that specific task, or inspects its `.Exception` property.
*   **async void**: The exception escapes the task pipeline completely and is thrown directly onto the active `SynchronizationContext`. Because the caller cannot await an `async void` method, this exception cannot be caught with a standard `try/catch` wrapper, which usually crashes the entire application process immediately. 
*   *Interview Pro-Tip*: State that `async void` should **only** be utilized for top-level UI event handlers (like button clicks) where async return constraints are structurally mandated.

## 4. Multi-Task Orchestration (`Task.WhenAll` vs. `Task.WhenAny`)

### The Panel Scenario
You need to pull case details concurrently from three separate regional courts to aggregate a legal background history check.

```csharp
var task1 = FetchGautengCourtAsync();
var task2 = FetchWesternCapeCourtAsync();
var task3 = FetchKznCourtAsync();
```

### Questions & Core Answers
*   **Q1: How do you await all three concurrently, and what happens if multiple tasks throw exceptions?**
    *   **Answer**: Use `await Task.WhenAll(task1, task2, task3);`. This executes the HTTP operations concurrently instead of sequentially. If multiple tasks fail, `Task.WhenAll` aggregates all exceptions into its internal collections, but standard `await` syntax will only rethrow the *first* exception. To inspect all failures, catch the statement and evaluate the `InnerExceptions` property of the task directly. TODO
*   **Q2: When would you purposefully choose `Task.WhenAny` instead?**
    *   **Answer**: Use `Task.WhenAny` when implementing performance **timeouts** or racing redundant tasks (e.g., calling two mirror database clusters and accepting the fastest responder to minimize user latency).

# C# Exception Handling Study Guide

### Example 1: `throw;` vs `throw ex;` (Stack Trace Erasure)

#### Question
What is the critical structural difference between using `throw;` and `throw ex;` inside a `catch` block in C#? Provide code snippets illustrating the effect on the exception stack trace.

#### Answer
The fundamental difference lies in **how the stack trace data is preserved**. 

* **`throw;`** rethrows the exception while **preserving the original stack trace**. It maintains the exact original location (method and line number) where the exception was first thrown.
* **`throw ex;`** **resets the stack trace**, overwriting the origin. It tricks the runtime into thinking the exception originated exactly at the line where `throw ex;` is called, erasing the history of the actual root cause deep within the call stack.

##### Correct Pattern: `throw;`
```csharp
public void ProcessData()
{
    try
    {
        // Imagine an error happens deep inside this method
        ExecuteDatabaseQuery(); 
    }
    catch (Exception ex)
    {
        LogFailure(ex.Message);
        
        // ✅ Keeps the original stack trace leading back to ExecuteDatabaseQuery()
        throw; 
    }
}
```

##### Antipattern: `throw ex;`
```csharp
public void ProcessData()
{
    try
    {
        ExecuteDatabaseQuery(); 
    }
    catch (Exception ex)
    {
        LogFailure(ex.Message);
        
        // ❌ Erases the history. The logs will claim the error started right here.
        throw ex; 
    }
}
```

### Example 2: `Task.WhenAll` with Multiple Exceptions

#### Question
Consider a `Task.WhenAll` call tracking multiple parallel operations (e.g., a primary cluster node and a replica node). If **both** operations fail concurrently and throw completely different exceptions, what happens to the secondary exception inside the `catch (Exception ex)` block? How do you ensure both exceptions are caught and logged?

```csharp
public async Task<List<StatutePayload>> CompileStatuteReportAsync(string actId)
{
    var primaryTask = FetchFromPrimaryNodeAsync(actId);
    var replicaTask = FetchFromReplicaNodeAsync(actId);

    try
    {
        await Task.WhenAll(primaryTask, replicaTask);
    }
    catch (Exception ex)
    {
        // PANEL TRAP: If BOTH nodes fail and throw different exceptions, 
        // what happens to the secondary exception log entry here?
        Console.WriteLine(\$"Error recorded during cluster sync: {ex.Message}");
        throw;
    }

    return new List<StatutePayload> { primaryTask.Result, replicaTask.Result };
}
```

#### Answer
When `await Task.WhenAll(...)` encounters failures across multiple tasks, the `catch (Exception ex)` block **only captures the very first exception** (typically from whichever task completed and failed first). The secondary exception is **completely hidden from the `catch` block variable (`ex`)** and will not be logged by your `Console.WriteLine` statement.

However, because the code uses `throw;`, the full multi-exception state isn't destroyed; it is propagated up to the caller as an aggregated state. If you need to log **every** exception that occurred during the concurrent execution right inside this method, you must bypass the unwrapped `ex` variable and inspect the `.Exception` property of the tracked `Task.WhenAll` object directly.

##### Fixed and Complete Solution
```csharp
public async Task<List<StatutePayload>> CompileStatuteReportAsync(string actId)
{
    var primaryTask = FetchFromPrimaryNodeAsync(actId);
    var replicaTask = FetchFromReplicaNodeAsync(actId);
    
    // 1. Keep a direct reference to the multi-task tracking wrapper
    var allTasks = Task.WhenAll(primaryTask, replicaTask);

    try
    {
        await allTasks;
    }
    catch (Exception)
    {
        // 2. Safely access the full AggregateException containing ALL failures
        if (allTasks.Exception != null)
        {
            foreach (var innerEx in allTasks.Exception.InnerExceptions)
            {
                // ✅ Loops through and logs both the primary and replica exceptions
                Console.WriteLine(\$"Error recorded during cluster sync: {innerEx.Message}");
            }
        }
        
        // 3. Rethrow safely using 'throw;' to preserve the exact multi-exception task state
        throw;
    }

    return new List<StatutePayload> { primaryTask.Result, replicaTask.Result };
}
```
