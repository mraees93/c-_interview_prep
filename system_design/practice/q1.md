# LexisNexis Interview Preparation Master File
**Target Company:** LexisNexis Cape Town  
**Role Level:** Intermediate Software Engineer  
**Case Study:** Premium Legal Document Search & Alert System

---

## 1. System Requirements

*   **Search Feature:** Users must be able to search through documents using complex keywords. Search results must return in under one second.
*   **Alert Feature:** Users can save their search queries as automated alerts. When a new document matches their query, they must receive an email notification.
*   **System Scale:** The system holds 50 million total legal documents. It receives 10,000 new document uploads every single day.
*   **User Traffic:** 100,000 active daily users querying the system.

### Flow Walkthrough Comments:

#### The Read Search Flow (Steps R1 to R3b)
*   **[R1]**: The user enters a keyword query (e.g., *"breach of contract"*) into the legal application interface.
*   **[R2]**: The API Gateway paths the search query directly to the dedicated **Search Service**.
*   **[R3a] (Cache Lookaside)**: The Search Service checks the **Redis Cache** first using a hash of the search string. If it finds the results (Cache Hit), it serves them instantly, bypassing downstream services.
*   **[R3b] (Cache Miss)**: If the search query isn't in Redis, the service queries the **Elasticsearch Cluster**, returns the data to the user, and asynchronously populates Redis with a set Time-To-Live (TTL) for next time. 

tip: On a cache miss, I fetch from Elasticsearch. To keep user latency as low as possible, I return the data to the user immediately and populating the Redis cache happens asynchronously in the background so it doesn't block the user's thread.

#### The Write & Alert Flow (Steps W1 to W5)
*   **[W1]**: A court data pipeline uploads a batch of new documents to the platform.
*   **[W2a]**: The Ingestion Service writes the primary document information and database rows straight into the **PostgreSQL Primary DB**.
*   **[W2b]**: At the exact same time, the Ingestion Service fires a background message to **Apache Kafka** stating that a new document has officially entered the system.
*   **[W3]**: A background Change Data Capture (CDC) engine automatically reads the new PostgreSQL database transaction records and updates the **Elasticsearch** indexes so the new document is searchable.
*   **[W4]**: The **Alert Workers** continuously pull messages out of the Kafka queue to find out what new documents have arrived.
*   **[W5]**: The worker checks if the document text matches any user's saved query criteria, then routes a job payload directly to the **Email Provider** to alert the user.

## 3. The 6 Interview Questions, Answers, & Explanations

### Question 1: Data Storage Choice
*   **Question:** How will you choose to store the 50 million legal documents?
*   **Your Answer:** "I chose postgresql db, replication."
*   **Full Explanation Answer:** PostgreSQL with replication is an excellent choice. At 50 million records, relational metadata handles easily. However, legal documents contain giant walls of text. To prevent database page bloat, the metadata (author, date, case ID) should live in PostgreSQL, while the raw text files are offloaded to an Object Store (like AWS S3 or Azure Blob Storage) with their file URLs saved in the database. Read replicas are added to separate heavy search lookups from the primary node.

### Question 2: Complex Phrase Search Engine
*   **Question:** Legal users search for complex phrases like *"breach of contract AND damages"*. Are you using standard database indexes, or offloading this to an external tool?
*   **Your Answer:** "i'll use elasticsearch"
*   **Full Explanation Answer:** This is the ideal architectural decision. Relational databases struggle with heavy full-text wildcard queries across millions of large files. Elasticsearch creates an inverted index of words, allowing it to process tokenized, linguistic text searches in milliseconds without draining the main database's CPU.

### Question 3: Notification Tooling
*   **Question:** Which tool will you use to trigger and handle the email alert delivery system safely?
*   **Your Answer:** "I trigger emails using message queue kafka"
*   **Full Explanation Answer:** Spot on. Apache Kafka decouples the document ingestion service from the notification pipeline. Instead of forcing the primary document upload service to wait for emails to process, it broadcasts a quick event to a Kafka topic, allowing backend workers to handle notification delivery asynchronously.

### Question 4: Sharding Strategy
*   **Question:** What will you use as your Shard Key to split your database data across multiple servers horizontally?
*   **Your Answer:** *(Unsure during initial prompt)*
*   **Full Explanation Answer:** The most optimal shard key for a legal platform is a geographic or structural indicator like `Jurisdiction_ID` or `Region_ID` (e.g., Western Cape High Court). Legal professionals almost always limit their searches to specific court regions. Sharding by region keeps localized queries on a single server node. To avoid "hot shards" (one court getting too much data), a composite key like `Jurisdiction_ID + Year` can be used.

### Question 5: Indexing Trade-offs
*   **Question:** Every time 10,000 new documents are uploaded daily, indexes must rewrite. How do you balance indexing frequently accessed columns without hurting write speeds?
*   **Your Answer:** "I plan to use indexing (the frequently accessed columns) and sharding."
*   **Full Explanation Answer:** Indexes speed up reading data but slow down writing data because the database must recalculate its index trees on every insert. To balance this, the PostgreSQL Primary database keeps indexes down to a bare minimum (Primary Keys and Foreign Keys only). Heavy read indexes are instead pushed to the Read Replicas and the Elasticsearch text clusters.

### Question 6: Resiliency and Failure Modes

#### Scenario A: The Third-Party Email Service Crashes
*   **Question:** The email delivery provider crashes for 4 hours. What happens to the thousands of alert emails waiting to go out?
*   **Your Answer:** *(Unsure during initial prompt)*
*   **Full Explanation Answer:** Because the design includes **Apache Kafka**, the emails are perfectly safe. Kafka acts as a durable shock absorber and saves data streams directly to its disk logs. The notification workers will pause and stop advancing their queue position. Once the email service recovers, the workers wake up and process the backlogged messages right from where they stopped, ensuring zero email data loss.

#### Scenario B: Keeping PostgreSQL and Elasticsearch in Sync
*   **Question:** A document saves to PostgreSQL, but the system crashes before writing it to Elasticsearch. How do you ensure they stay synchronized?
*   **Your Answer:** "i'll ensure there are replicas before building this entire system, i can also add another replica"
*   **Full Explanation Answer:** Adding database replicas keeps data highly available, but to maintain strict sync consistency between a relational database and a search engine, you should use **Change Data Capture (CDC)** tools like Debezium. The CDC tool constantly watches the PostgreSQL write logs. The exact millisecond a write registers in PostgreSQL, the CDC engine reads the log and automatically pipes that data update straight into Elasticsearch.

#### Scenario C: High Availability and Hardware Failure
*   **Question:** The primary database machine overheats and crashes physically. What automatically happens next so the website stays online?
*   **Your Answer:** "i'll use a failover before building this entire system so it instantly switches traffic to a standby node upon failure."
*   **Full Explanation Answer: This is exactly correct. The system uses a synchronous, replication-linked Standby Node. A cluster health broker monitors the active     primary instance. The moment it detects a heartbeat failure, it runs an automated failover, promotes the standby replica to become the new live Primary database, and reroutes API traffic instantly with minimal disruption.
